Preparation — Service inventory and baseline

Step 1 — Record the service inventory and baseline

Identify your hostname, IP, listeners and running services. Compare with Overview.

hostname

Display the VM’s network addresses and routing table:

ip -br address

Inspect listening ports and their owning processes:

sudo ss -lntup

Inspect service status and recent service messages:

systemctl status nginx ssh --no-pager

Inspect the firewall state and configured rules:

sudo ufw status verbose

Module 1 — Attacker already has system access

Task 1.1 — Service tampering and recovery

Roles and command windows: each team runs only its assigned steps in its own terminal or PowerShell window. Attacker commands do not inherit defender variables. Run each role’s setup commands in that role’s window; keep it open for that role’s later steps. Defender baselines and recovery files remain with the defender. Scenario preparation changes the lab state, but does not require the attacker to run defender commands. For Module 2, attacker actions run outside the target VM; Task 2.2 login attempts are instructor-operated.

Practice responding to a service outage caused by an attacker who already has administrative access. The attacker stops the web service, and the defender investigates, restores it, and verifies recovery. Use the role-specific steps below.

Task 1.2 — Web-content tampering and evidence

Investigate unauthorized changes to a webpage even when the web service still responds. Use the role-specific steps below.

Round order: the defender completes Defender step 1 before the attack. Then follow the handoffs below. Each role uses its own command window and numbered steps.

Attacker

Step 1 — Changes the page

Open your own Terminal inside the Ubuntu VM. The commands below use the webpage’s full path and require no variables or recovery files from Defender step 1.

In the Ubuntu VM, record the time and replace only the exercise webpage with the marker below. Keep Nginx, SSH and remote desktop running. Do not modify your recovery copy or baseline checksum. Hand over to the defender after the change.

Record the time for comparison with the evidence:

date -u

Replace only the exercise webpage with the assigned changed-page marker:

printf '%s\n' '<!doctype html><html lang="en"><title>CCDC exercise</title><p>CCDC exercise: changed page</p></html>' | sudo tee /var/www/html/index.html

Check the service states and request the webpage; compare both with the expected results for this step:

systemctl is-active nginx ssh
curl --max-time 5 -i http://172.29.242.30/index.html

Official command documentation: tee

Expect HTTP 200 with the changed page. This is a content-integrity incident even though the service remains active.

Defender

Step 1 — Prepare a trusted recovery copy

Before the attack: complete this preparation, then tell the other team the lab is ready. Resume the remaining defender steps after the assigned action.

In Terminal inside your assigned Ubuntu VM, confirm the starting service state and webpage:

Check the service states and request the webpage; compare both with the expected results for this step:

systemctl is-active nginx ssh
curl --max-time 5 -fsS http://172.29.242.30/index.html

Both services should be active and the page should show CCDC Linux storefront: operational. Confirm the same content from your campus laptop at the Linux website. Continue only when the baseline is correct. If a previous round left the page changed, restore that round’s saved original using Defender step 3 before starting a new round; do not save the changed page as a trusted copy.

Before the attack, run the following commands one at a time to create a new exercise directory and save the original page and baseline checksum yourselves. Check each result before continuing. The defender keeps this Terminal open for the defender investigation and recovery steps. The attacker uses a separate Terminal for Attacker step 1. When you switch roles, repeat Defender step 1 to create a new directory for the next round. The previous round’s files remain saved.

Create a new directory for this round’s recovery files or evidence:

case_dir=$(mktemp -d "$HOME/CCDC-Exercise-1-2.XXXXXX")

Check the service states and request the webpage; compare both with the expected results for this step:

systemctl is-active nginx ssh
curl --max-time 5 -fsS http://172.29.242.30/index.html

Save a recovery copy of the operational page:

sudo cp -a /var/www/html/index.html "$case_dir/original.html"

Save the page’s SHA-256 checksum:

printf '\nExercise directory: %s\n' "$case_dir"

Note: in a real environment, store the trusted recovery copy and baseline checksum outside the victim computer so an attacker who compromises that computer cannot alter them.

Step 2 — Investigates before restoring

Return to your defender Terminal from Defender step 1. If it was closed, set case_dir to the recorded recovery-directory path before continuing. Do not save the changed page as a new baseline.

From your campus laptop, open the Linux website with a fresh request and confirm that the operational content has changed. Then run the following inside the Ubuntu VM to preserve evidence in a separate folder within this round’s exercise directory:

Set the evidence-folder path and create the folder with access limited to your trainee account:

evidence_dir="$case_dir/evidence"
mkdir -m 700 "$evidence_dir"

Record the changed file’s metadata and checksum as evidence:

sudo stat /var/www/html/index.html | tee "$evidence_dir/stat.txt"
sudo sha256sum /var/www/html/index.html | tee "$evidence_dir/hash.txt"

Save the changed page before recovery:

sudo cat /var/www/html/index.html > "$evidence_dir/page.txt"

Save the relevant log records in the evidence folder:

sudo journalctl -u nginx --since "20 minutes ago" --utc --no-pager > "$evidence_dir/nginx-journal.txt"

Inspect the latest web access records and save them as evidence:

sudo tail -n 100 /var/log/nginx/access.log > "$evidence_dir/access.txt"

Request the webpage and compare the response with the expected result for this step:

curl -i http://172.29.242.30/index.html

Official command documentation: mkdir · stat · cat · tail

Compare the changed file’s hash with the checksum you saved in Defender step 1 using the read-only command below. A mismatch is expected after the attack; it confirms that the webpage differs from the baseline. Preserve the changed page before recovery. File timestamps and service logs alone do not establish who edited the page.

sudo sha256sum -c "$case_dir/original.sha256"

Restore the original page saved before the attack:

sudo cp -a "$case_dir/original.html" /var/www/html/index.html

Task 1.3 — Firewall rule configuration and recovery

Investigate an HTTP outage caused by a firewall change while the web service remains running. Use the role-specific steps below.

Round order: the defender completes Defender step 1 before the attack. Then follow the handoffs below. Each role uses its own command window and numbered steps.

Attacker

Step 1 — Block incoming HTTP traffic

Run the guest commands in Terminal inside your assigned Ubuntu VM. First inspect the existing firewall rules and services:

Inspect the current numbered firewall rules and whether UFW is active:

sudo ufw status numbered

Check the service states and request the webpage; compare both with the expected results for this step:

systemctl is-active nginx ssh xrdp
curl --max-time 5 -fsS http://127.0.0.1/index.html

UFW must report Status: active, all three services must be active and the local page must show the operational storefront. From your campus laptop, open the Linux website with a fresh request and confirm the same page. Do not continue until these baseline checks pass. If a rule marked CCDC-Exercise-1-3 is already present, complete Defender step 3 before starting a new round.

Record the time, then add the following HTTP-only rule once:

Record the time for comparison with the evidence:

date -u

Add the labeled HTTP-only exercise rule once:

sudo ufw insert 1 deny in proto tcp from 172.29.242.0/24 to any port 80 comment 'CCDC-Exercise-1-3'

Inspect the current numbered firewall rules and whether UFW is active:

sudo ufw status numbered

The rule is placed before the existing HTTP allow rule. It blocks incoming TCP port 80 from the lab subnet, including requests forwarded by the campus relay. It does not block SSH on port 22 or remote desktop on port 3389. Leave Nginx running and keep your remote desktop session open. Do not change other firewall rules or the host firewall.

From your campus laptop, make a fresh request to the same website. Expect a timeout, request failure or relay error instead of the operational page. A successful TCP connection to the relay alone does not establish HTTP availability. Hand over to the defender after demonstrating the failure.

Defender

Step 1 — Configure and test an allow rule

Before the attack: complete this preparation, then tell the other team the lab is ready. Resume the remaining defender steps after the assigned action.

Practice reading and configuring a rule before the attack round. Confirm the firewall is active, normal laptop HTTP works, and the instructor has a guest recovery console. Save the initial rule listing. Keep existing rules, default policies and SSH/RDP access unchanged.

Rule fieldValue and purpose
Direction and actionInbound allow: permit requests arriving at the VM.
Protocol and portTCP 80 on the guest, not the laptop-facing relay port.
Source address172.29.242.1, the relay address normally seen in guest logs. Confirm it using an actual laptop request.
Destination addressThe assigned VM’s internal address.

A scoped allow rule does not remove broader existing permissions. This exercise teaches rule construction and troubleshooting; it does not establish that all other sources are blocked.

In the Ubuntu terminal, inspect the policy and numbered rules:

sudo ufw status verbose
sudo ufw status numbered

If an equivalent allow rule already exists, inspect it and skip creating or deleting it. Otherwise preview and add this temporary rule:

sudo ufw --dry-run allow in proto tcp from 172.29.242.1 to 172.29.242.30 port 80 comment 'CCDC-Exercise-1-3-Allow'
sudo ufw allow in proto tcp from 172.29.242.1 to 172.29.242.30 port 80 comment 'CCDC-Exercise-1-3-Allow'
sudo ufw status numbered

--dry-run previews the change; from selects the source and to … port 80 selects the destination service. Confirm a fresh laptop request to the Linux website returns operational content. Existing rules may also allow this traffic. Continue with the attack below; its deny rule is inserted before ordinary UFW user allow rules.

Step 2 — Investigate the outage

Before changing anything, run the following inside the Ubuntu VM:

Record the time for comparison with the evidence:

date -u

Check the service states and request the webpage; compare both with the expected results for this step:

systemctl is-active nginx ssh xrdp
curl --max-time 5 -fsS http://127.0.0.1/index.html

Inspect the listening ports and current firewall rules:

sudo ss -lntp 'sport = :80'
sudo ufw status numbered

Record the output or screenshots. Nginx should remain active, port 80 should still have a listener and the loopback request should return the operational page. Identify the CCDC-Exercise-1-3 deny rule above the HTTP allow rule and record its source subnet, destination port and position. Compare this with the failed laptop request.

Explain why the evidence points to network filtering rather than a stopped web service. A successful loopback request tests the local service; it does not prove that requests from outside the VM are allowed.

Step 3 — Recover and verify

After preserving the evidence, remove only the exact exercise rule using the command below. Leave UFW enabled and preserve the existing allow rules:

Remove only the exact HTTP exercise rule:

sudo ufw delete deny in proto tcp from 172.29.242.0/24 to any port 80 comment 'CCDC-Exercise-1-3'

Inspect the current numbered firewall rules and whether UFW is active:

sudo ufw status numbered

Check the service states and request the webpage; compare both with the expected results for this step:

systemctl is-active nginx ssh xrdp
curl --max-time 5 -fsS http://127.0.0.1/index.html

Record the time for comparison with the evidence:

date -u

Confirm that UFW remains active, the exercise deny rule is absent and the original allow rules remain. Repeat the laptop HTTP request with a fresh request; it must now return the operational storefront. All three services should still be active and your remote desktop session should remain connected.

Step 4 — Restore the original policy

Only if you created the allow rule during this round, remove it now. Skip this command if the equivalent rule existed before the exercise:

sudo ufw delete allow in proto tcp from 172.29.242.1 to 172.29.242.30 port 80 comment 'CCDC-Exercise-1-3-Allow'
sudo ufw status numbered

Compare the final rules with the saved baseline. Recheck external HTTP and legitimate remote access. Explain the direction, source, destination, port and precedence of the rules before reversing roles. Test with fresh requests because an existing connection may not reflect a new rule.

Reference: UFW rule syntax.

Practice check: show the external HTTP failure, the running local service, the exercise rule and successful external recovery after removing that rule. Explain how this differs from Task 1.1. Keep your evidence, then reverse attacker and defender roles and repeat from Attacker step 1. No written report submission is required.

Task 1.4 — Compromised account and excessive privilege

Investigate an exercise account with excessive privileges and contain its access while preserving legitimate services. Complete the four steps below yourselves, then switch roles and repeat.

Use only the dedicated ccdc-demo account for this exercise. Keep your assigned trainee account’s privileges unchanged. This task starts with access to an account; it does not involve guessing or cracking passwords.

Round order: Each role uses its own command window and numbered steps.

Attacker

Step 1 — Prepare the dedicated exercise account

The attacker performs this setup and Attacker step 2 in their own VM session, using the temporary password they set here. The defender starts at Defender step 1 in a separate command window and discovers the account independently.

In Terminal inside the Ubuntu VM, use your assigned trainee account with sudo. Run each command separately and check its result before continuing.

Check the service states and request the webpage; compare both with the expected results for this step:

systemctl is-active nginx ssh xrdp
curl --max-time 5 -fsS http://172.29.242.30/index.html

All three services should be active and the page should show the operational storefront. Confirm the same page from your campus laptop at the Linux website.

Check whether the exercise account already exists:

getent passwd ccdc-demo

Expect no output. Then check for an existing exercise sudo rule:

sudo ls -l /etc/sudoers.d/ccdc-exercise-1-4

Expect a “No such file or directory” message. If either the account or rule exists, finish the previous round’s cleanup before continuing. Do not overwrite an existing rule.

Create the dedicated exercise account:

sudo useradd --create-home --shell /bin/bash --comment 'CCDC Task 1.4 exercise account' ccdc-demo

Set its temporary exercise password and share it with the student acting as attacker:

sudo passwd ccdc-demo

The password characters will not appear as you type. Enter the same temporary password twice.

Open a new exercise sudo rule in Nano using the syntax-checking sudoers editor:

sudo EDITOR=nano visudo -f /etc/sudoers.d/ccdc-exercise-1-4

Enter this single line in the editor. It grants permission only to stop Nginx:

ccdc-demo ALL=(root) NOPASSWD: /usr/bin/systemctl stop nginx

Press Ctrl+O, then Enter to save, and Ctrl+X to exit. If visudo reports a syntax error, choose to edit again and correct the line; do not force it to save an invalid rule.

Check that the sudo configuration is valid:

sudo visudo -c

Confirm the exercise account does not belong to the sudo group:

id ccdc-demo

Check its granted command:

sudo -l -U ccdc-demo

The listed permission should be limited to /usr/bin/systemctl stop nginx. Continue only after the syntax check passes and the account has the expected privilege.

Official command documentation: getent · visudo · useradd · passwd · nano · id

Step 2 — Demonstrate the excessive privilege

Open a second Terminal inside the same Ubuntu desktop. Switch only this shell to the exercise account, entering its temporary password:

su - ccdc-demo

Confirm that whoami prints ccdc-demo, then stop Nginx using the granted command:

Confirm the exercise account’s identity and inspect its permitted sudo commands:

whoami
sudo -l

Record the time for comparison with the evidence:

date -u

Attempt to stop Nginx using the exercise account’s granted command:

sudo -n /usr/bin/systemctl stop nginx

Official command documentation: su · whoami

The stop command should succeed without a sudo password prompt. From your campus laptop, request the website again; it should no longer return the operational page. Leave this exercise shell open for the containment test. Do not stop SSH or remote desktop, and do not change any other service, account or rule.

Defender

Step 1 — Investigate and contain

Open your own defender Terminal running as your assigned trainee account. Keep this Terminal open through Defender step 2. Record the account, the sudo grant, service state and relevant events:

Create a new directory for this round’s recovery files or evidence:

case_dir=$(mktemp -d "$HOME/CCDC-Exercise-1-4.XXXXXX")

Record the time for comparison with the evidence:

date -u

Record the exercise account’s identity, groups and sudo permissions:

id ccdc-demo | tee "$case_dir/account.txt"
sudo -l -U ccdc-demo 2>&1 | tee "$case_dir/sudo-permissions.txt"

Save the exercise sudo rule before removing it:

sudo cat /etc/sudoers.d/ccdc-exercise-1-4 | tee "$case_dir/sudo-rule.txt"

Check and record the service states in the evidence file:

systemctl is-active nginx ssh xrdp | tee "$case_dir/services-before.txt"

Save the Nginx and sudo log records for the exercise time window:

sudo journalctl -u nginx --since '20 minutes ago' --utc --no-pager > "$case_dir/nginx-journal.txt"
sudo journalctl _COMM=sudo --since '20 minutes ago' --utc --no-pager > "$case_dir/sudo-journal.txt"

Nginx should be inactive while SSH and remote desktop remain active. The saved rule and permission listing establish the excessive access. Available logs may help establish timing; a missing event does not prove an action did not occur.

Remove only the exercise sudo rule, validate the remaining policy and restore Nginx. Run each command separately; continue past the policy check only if it reports that the configuration parsed successfully:

Remove only the exercise sudo grant:

sudo rm /etc/sudoers.d/ccdc-exercise-1-4

Validate the remaining sudo configuration; expect a successful parse before continuing:

sudo visudo -c

Start Nginx to restore the web service:

sudo systemctl start nginx

Official command documentation: rm

Step 2 — Verify containment and clean up

In the attacker’s existing ccdc-demo shell, repeat exactly the same command:

sudo -n /usr/bin/systemctl stop nginx

Expect denial, such as a password-required or not-allowed message. Do not enter another account’s password or rerun the test from the trainee shell: that account intentionally retains sudo access. In the defender Terminal, confirm that the denied attempt did not stop Nginx:

Check the service states and request the webpage; compare both with the expected results for this step:

systemctl is-active nginx ssh xrdp
curl --max-time 5 -fsS http://172.29.242.30/index.html

Repeat the laptop HTTP check; it must return the operational storefront. Revoking sudo does not end an existing shell. In the attacker Terminal, run exit to leave the exercise account, and close any other shells or processes you started as that account. In the defender Terminal, remove only the dedicated exercise account and its home folder after retaining the evidence in your trainee account’s exercise directory:

Remove only the dedicated exercise account and its home folder:

sudo userdel --remove ccdc-demo

Confirm the exercise account has been removed; expect no output:

getent passwd ccdc-demo

Check that the exercise sudo rule is absent and immediately display the result code; expect 0:

sudo test ! -e /etc/sudoers.d/ccdc-exercise-1-4
echo $?

Check and record the service states:

systemctl is-active nginx ssh xrdp

Official command documentation: userdel

Expect no account output from getent, result code 0 for the absent exercise sudo rule, and active services. Keep the evidence, reverse roles and repeat from Attacker step 1 with a fresh exercise account.

Practice check: show the successful attacker action, saved account and privilege evidence, the denied repeat attempt and normal service after recovery. Explain why removing this permission differs from merely restarting Nginx. No written report submission is required.

Task 1.5 — Suspicious outbound traffic and data exfiltration

Identify a process sending dummy business data out of the victim VM, contain the connection and verify normal service. Use the role-specific steps below.

This exercise uses curl as a visible simulator and sends only the supplied fictional records. The receiver at 172.29.242.1:18081 is on the isolated lab host, outside the victim VM. It accepts only the exact dummy payload. No startup mechanism is installed. Use only this destination and the supplied file.

Round order: the defender completes Defender step 1 before the attack. Then follow the handoffs below. Each role uses its own command window and numbered steps.

Attacker

Step 1 — Prepare the dummy file and start the transfer

Open your own Terminal inside the assigned VM. Complete the file setup below in this window; no variables from the defender’s Defender step 1 are needed.

Use your assigned trainee account in Terminal inside the Ubuntu VM. Download the dummy business-data file unchanged into Downloads inside the VM. If using an offline copy of this pack, copy the same file from lab-assets into Downloads.

Create a fresh exercise directory and display its path:

case_dir=$(mktemp -d "$HOME/CCDC-Exercise-1-5.XXXXXX")
