Module 1 — Attacker already has system access

Read Module 1 concepts and the exercise workflow in Getting Started, then complete these platform tasks.

1.1 — Service tampering and recovery

Location: service and investigation commands run in Terminal INSIDE the Ubuntu VM (ccdc-linux, 172.29.242.30). The explicitly labeled laptop browser checks run on your own computer outside the VM. No Windows commands or Windows login are needed. Use trainee01 with sudo; enter TrainLab!2601 when prompted.

Scenario: the attacker already has administrative access and deliberately stops a business service. This is a controlled simulation of privileged-account misuse, not a remote exploit or password attack.

Roles: one attacker, one defender and one observer. Because they share the same desktop/account, take turns at the keyboard: attacker performs the assigned action, then hands over to the defender. The observer records UTC times. Do not open competing trainee01 desktop sessions. Do not stop SSH, xrdp or networking.

Step 1 - Verify the Linux baseline

Verify the relevant services and record the results. 

date -u
hostname
systemctl is-active nginx ssh
curl --max-time 5 -fsS http://172.29.242.30/index.html

Understand these commands: hostname · systemctl · curl · date

Laptop browser check — baseline

Location: your own computer, outside the VM. Before the attacker stops the service, confirm the website works from your own campus laptop. Open http://128.198.74.133:18080/index.html. Hard-refresh to avoid a cached page, or use the command below for a new request. Keep this separate from the guest-side commands above.

Windows laptop, PowerShell:

curl.exe -i --max-time 5 http://128.198.74.133:18080/index.html

Understand these commands: curl

macOS/Linux laptop, Terminal:

curl -i --max-time 5 http://128.198.74.133:18080/index.html

Understand these commands: curl

Expect HTTP 200 and the page text CCDC Linux storefront: operational. Compare the response with the service state and timestamps inside the target VM. The relay's TCP port can still accept a connection when the guest HTTP service is down: a successful port test alone does not prove HTTP works. This is an HTTP service exercise; do not stop networking, RDP or TCP itself.

Step 2 - Linux attacker action

Record the time, stop Nginx once, then hand over. Do not change anything else.

date -u
sudo systemctl stop nginx

Understand these commands: sudo · systemctl · date

Laptop browser check — outage

Location: your own computer, outside the VM. With the HTTP service stopped, test again from your own campus laptop before the defender restores it. Open http://128.198.74.133:18080/index.html. Hard-refresh to avoid a cached page, or use the command below for a new request. Keep this separate from the guest-side commands above.

Windows laptop, PowerShell:

curl.exe -i --max-time 5 http://128.198.74.133:18080/index.html

Understand these commands: curl

macOS/Linux laptop, Terminal:

curl -i --max-time 5 http://128.198.74.133:18080/index.html

Understand these commands: curl

Expect a request failure, empty reply, timeout or HTTP error; the operational page must not be returned. IIS can return an HTTP error while its HTTP.sys TCP listener remains available. Compare the response with the service state and timestamps inside the target VM. The relay's TCP port can still accept a connection when the guest HTTP service is down: a successful port test alone does not prove HTTP works. This is an HTTP service exercise; do not stop networking, RDP or TCP itself.

Step 3 - Linux defender investigation

Confirm the outage before changing the system. A failed curl and an inactive service are expected in this round. Record output or screenshots; the journal provides evidence of a service change, not necessarily the actor's identity.

1.2 — Web-content tampering and evidence

Shared concept →

Objective: distinguish an intact service from correct business content. Instructor introduces an altered Linux page.

Defender, Linux guest; use a new evidence directory for this round:

case_dir="$HOME/case-$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -m 700 "$case_dir"
sudo stat /var/www/html/index.html | tee "$case_dir/stat.txt"
sudo sha256sum /var/www/html/index.html | tee "$case_dir/hash.txt"
sudo cat /var/www/html/index.html > "$case_dir/page.txt"
sudo journalctl -u nginx --since "20 minutes ago" --utc --no-pager > "$case_dir/nginx-journal.txt"
sudo tail -n 100 /var/log/nginx/access.log > "$case_dir/access.txt"
curl -i http://172.29.242.30/index.html

Understand these commands: sudo · curl · date · journalctl · mkdir · stat · sha256sum · cat · tee · tail · script syntax

Request the instructor's trusted backup after collecting evidence, restore it, and verify content. Do not copy the attacker's altered page into the baseline.

Practice check: demonstrate the result, explain your actions to your group, and retain your working files. No written report submission is required.

1.3 — Firewall tampering versus service failure

Shared concept →

Instructor blocks Linux HTTP through a temporary guest firewall rule. Defender must preserve SSH and console access.

Linux guest:

systemctl is-active nginx
curl -fsS http://127.0.0.1/index.html
sudo ss -lntp
sudo ufw status numbered

Understand these commands: sudo · ss · systemctl · ufw · curl

Ask the instructor to test HTTP and SSH from outside the Ubuntu VM before and after recovery. Local loopback success alone does not prove external access.

Identify the instructor's exercise rule. Remove that rule only, then retest externally. Do not disable the entire firewall or alter the host firewall.

Practice check: demonstrate the result, explain your actions to your group, and retain your working files. No written report submission is required.

1.4 — Compromised account and excessive privilege

Shared concept →

Instructor creates an exercise-only Linux account with one deliberately excessive sudo permission: stopping Nginx. This is a supplied compromised-account scenario, not password cracking.

Attacker, in the provided exercise account's guest session:

whoami
sudo -l
sudo /usr/bin/systemctl stop nginx

Understand these commands: whoami · sudo · systemctl

Defender: inventory the exercise account and its sudo rule, preserve the relevant sudo/journal records, revoke the unnecessary permission and restore Nginx. Ask the instructor to retest the same command as the exercise account; it should be denied while HTTP remains available.

Practice check: demonstrate the result, explain your actions to your group, and retain your working files. No written report submission is required.

Module 2 — Attacker starts without system access

Read Module 2 concepts and exercise boundaries in Getting Started, then complete the platform tasks below. This track includes a bounded port pass, request-log investigation and a supplied DoS evidence exercise.

2.1 — Port scanning and service discovery

Use the assigned guest only. In these single-VM simulations, the red-team operator uses a normal guest terminal to generate network requests; target administration is reserved for the blue team. The operator login is a traffic-generation convenience, not evidence of a successful intrusion. Do not elevate the red-team commands.

Blue team — establish the service inventory

Record listening ports before the red-team pass. The instructor confirms TCP 65000 is unused; if it is in use, omit it. Required ports are 22 (SSH), 80 (HTTP), and 3389 (RDP).

date -Is
sudo ss -lntup
systemctl is-active nginx ssh xrdp

Red team — one bounded pass

Probe only these four ports once. A failed connection can mean a closed port or filtering; it is not a conclusive firewall diagnosis. Save the displayed results for comparison.

for port in 22 80 3389 65000; do
  if timeout 2 bash -c "exec 3<>/dev/tcp/172.29.242.30/$port" 2>/dev/null; then
    printf '%s open\n' "$port"
  else
    printf '%s closed-or-filtered\n' "$port"
  fi
done

Blue team — explain and verify

  1. Compare probe results with the inventory. Explain each expected listener and investigate any discrepancy.
  2. Inspect existing firewall or service logs for the recorded time window. A connection-only probe may leave no application log entry. Report that visibility gap rather than inventing evidence.
  3. Explain one restriction you would consider for an unnecessary service. This round changes no firewall or service configuration.
  4. Use a fresh laptop request to the assigned website to confirm ordinary HTTP still works.

Complete: show the four results, the matching listener inventory, and a normal HTTP response. No configuration cleanup is needed. The local pass does not establish laptop reachability or test the relay firewall. Windows TCP 53 does not verify UDP DNS.

2.2 Investigate failed SSH authentication

Defender, Ubuntu terminal: establish the baseline and note the current time. The instructor must confirm the test account does not exist. If getent prints an account, stop and ask for a different test name.

date -Is
getent passwd ccdc-probe-no-user
systemctl is-active ssh nginx
sudo journalctl -u ssh --since '10 minutes ago' --no-pager

Understand these commands: sudo · systemctl · date · journalctl · getent

Operator, a second Ubuntu terminal: this loopback exercise works without another group's VM. Run once, enter arbitrary dummy text at the password prompt, and expect Permission denied. Repeat manually at most twice more if instructed.

ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no -o NumberOfPasswordPrompts=1 ccdc-probe-no-user@127.0.0.1

On the first connection, verify the host key with the instructor before accepting it. This is a local SSH test: expect a loopback source, not an outside attacker address. For a network-source demonstration, the instructor may perform the same bounded test from the lab host to 172.29.242.30; students do not need host access.

sudo journalctl -u ssh --since '10 minutes ago' --no-pager
sudo journalctl -t sshd --since '10 minutes ago' --no-pager

Understand these commands: sudo · journalctl

The second query is a fallback if unit filtering misses SSH records. Find the test username, invalid-user or authentication-failure message, timestamp, source and source port. Distinguish log lines from attempts: one attempt can create several records. Explain why testing a nonexistent account demonstrates rejected authentication without risking a real account lockout. The journal is the primary source here; /var/log/auth.log may not exist on this VM.

2.3 Investigate web probing and a dummy exposed backup

The instructor first publishes the dummy exercise file. Operator, Ubuntu terminal: make these three requests, once each. The first is normal traffic; the last two model someone looking for files without logging in.

curl -i --max-time 5 http://172.29.242.30/index.html
curl -i --max-time 5 http://172.29.242.30/ccdc-probe-missing.txt
curl -i --max-time 5 http://172.29.242.30/ccdc-probe-backup.txt

Understand these commands: curl

Defender: inspect Nginx access records. Expect 200 for the normal page, 404 for the missing path and 200 with clearly labeled dummy text for the published backup. If results differ, inspect the setup rather than claiming success.

sudo tail -n 60 /var/log/nginx/access.log
sudo grep 'ccdc-probe-' /var/log/nginx/access.log | tail -n 20

Understand these commands: sudo · tail · script syntax

Locate the source, timestamp including timezone offset, method, request path and HTTP status. A request to a suspicious path shows probing; a 200 with the dummy content shows information was available without authentication. Neither alone proves command execution or a server takeover. Requests made on this server do not demonstrate an external network boundary.

Mitigate, repeat and verify

Preserve the relevant log entries before cleanup. Confirm that this exact file contains only the instructor's dummy marker. Then remove only the exercise file; keep Nginx and SSH running.

sudo cat /var/www/html/ccdc-probe-backup.txt
sudo rm -i /var/www/html/ccdc-probe-backup.txt
curl -i --max-time 5 http://172.29.242.30/ccdc-probe-backup.txt
curl -fsS --max-time 5 http://172.29.242.30/index.html
systemctl is-active nginx ssh
sudo tail -n 15 /var/log/nginx/access.log

Understand these commands: sudo · systemctl · curl · cat · tail · rm

Accept 404 for the removed file and the operational storefront for index.html. Observe both results in the log. Explain how removing exposed data changes the outcome even though requests can continue. For authentication, propose supported MFA, SSH keys or source restrictions and identify how each would be tested. Do not change SSH authentication, UFW rules or shared passwords during this round; those changes require a separate recovery plan.

Practice check: show one rejected SSH attempt and its evidence; show the web file before and after mitigation; explain one ordinary-error explanation and one suspicious pattern. State what the evidence cannot prove. Demonstrate a legitimate service check still passes. No written report is required.

References: Ubuntu journalctl manual; Nginx access logging.

2.4 — Investigate suspicious request traffic

Use the assigned guest only. In these single-VM simulations, the red-team operator uses a normal guest terminal to generate network requests; target administration is reserved for the blue team. The operator login is a traffic-generation convenience, not evidence of a successful intrusion. Do not elevate the red-team commands.

Prepare

The instructor confirms access logging is enabled and the two probe paths below do not exist. The blue team records the time and normal page response. This exercise uses web access logs as network-request evidence; it is not a packet-capture exercise.

Red team — generate a short request sequence

Run once: four sequential requests, separated by one second. The unique marker distinguishes the round from background traffic. Give the marker to the blue team after it locates the pattern.

marker="ccdc24-$(date +%s)"
printf 'Round marker: %s\n' "$marker"
for path in index.html ccdc24-missing.txt ccdc24-backup.zip index.html; do
  curl --max-time 5 -sS -o /dev/null -w '%{http_code} %{url_effective}\n' "http://172.29.242.30/$path?round=$marker"
  sleep 1
done

Blue team — find and interpret the evidence

sudo tail -n 120 /var/log/nginx/access.log | grep 'ccdc24-'

Use the actual configured log path if it differs. IIS records may be buffered: wait up to one minute and reread once. Read its #Fields header; the instructor should enable date, time, c-ip, cs-method, cs-uri-stem, cs-uri-query and sc-status. Nginx combined logs include the request path and query. Distinguish local time offsets from IIS UTC.

  1. Locate the four requests and record time, source, method, path and status.
  2. Explain why the two index requests are ordinary checks and why the backup-like path warrants investigation. Expected status order: 200, 404, 404, 200. If different, investigate the actual site configuration.
  3. Explain why a missing-file request does not demonstrate compromise. A source address identifies a connection, not a person.
  4. Propose one response if a sensitive backup really were exposed: preserve evidence and remove the exposed copy while leaving normal content available.

Verify and close the round

Repeat one normal index request and confirm operational content. Retain the relevant log lines; do not clear the logs. No files, accounts or rules were changed. Reverse roles with a new marker. Complete: show the ordered requests, explain their significance and uncertainty, and demonstrate normal service.

2.5 — Investigate denial of service and resource exhaustion

This is a concrete offline investigation using a supplied synthetic incident dataset. It does not generate a flood or change the live service. The red team introduces the incident evidence; the blue team diagnoses it, proposes containment, and validates the recovery evidence.

Open the evidence inside your assigned VM

Save the Linux incident CSV into Downloads inside the VM. If viewing this pack on a laptop, copy the CSV into the VM first. The commands below use that Downloads path; adjust it if needed. Each row is a one-minute measurement. requests and http_5xx are counts; p95_ms is the 95th-percentile response time in milliseconds; cpu_pct and memory_pct are percentages. The documentation-range source IP is fictional and must not be contacted.

Red team — present the scenario

Tell the blue team: “Users report slow pages and intermittent errors starting at 10:02 UTC. The service monitor still reports the web service running.” Provide the CSV. Do not stop the real service or send load traffic.

Blue team — analyze

python3 - <<'PYCODE'
import csv
from pathlib import Path
rows = list(csv.DictReader((Path.home() / 'Downloads/dos-linux-timeline.csv').open()))
for r in rows:
    errors = 100 * int(r['http_5xx']) / int(r['requests'])
    print(r['time_utc'], r['service_state'], 'requests='+r['requests'],
          'p95_ms='+r['p95_ms'], 'CPU='+r['cpu_pct'], f'5xx={errors:.1f}%')
peak = max(rows, key=lambda r: int(r['requests']))
print('Peak:', peak['time_utc'], peak['top_source'], peak['top_source_requests'])
PYCODE
  1. Identify the normal baseline, first degraded minute and peak minute. Calculate how much request volume increased from the baseline.
  2. Use service state, CPU, latency and error rate to distinguish this incident from the stopped-service exercise. Explain why these metrics alone cannot establish malicious intent.
  3. Calculate the busiest source’s fraction of requests at the peak. Propose a narrowly scoped request limit or upstream filter, and explain how you would avoid blocking legitimate users behind a shared gateway. Record the proposed action; do not apply it to this lab.
  4. Treat the 10:05 and 10:06 rows as supplied post-containment evidence. Verify recovery against the criteria below and explain what monitoring you would continue.

Recovery criteria and live service check

Accept the scenario recovery only if both final samples have a running service, p95 latency below 200 ms, error rate below 1%, and CPU below 50%. Then independently check the real VM with the read-only commands below. The live check demonstrates lab availability, not that you mitigated the synthetic incident.

systemctl is-active nginx
curl --max-time 5 -fsS http://172.29.242.30/index.html

Complete: present your timeline, calculations, diagnosis, proposed containment, and evidence that recovery criteria pass. Preserve your notes; deleting your downloaded CSV after the debrief is optional. Reverse roles with the other team explaining and challenging the diagnosis.
