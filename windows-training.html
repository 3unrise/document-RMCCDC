1.1 — Service tampering and recovery

Location: service and investigation commands run in PowerShell INSIDE the Windows VM (CCDC-WINDOWS, 172.29.242.40). The explicitly labeled laptop browser checks run on your own computer outside the VM. No Linux terminal or dig command is needed. Sign in as CCDC-WINDOWS rainee, open PowerShell with Run as administrator, and approve UAC.

Scenario: an attacker already has administrative access. These are two controlled service-stop rounds, not demonstrations of obtaining that access. Follow the red-team/blue-team exercise workflow. Do not stop Remote Desktop Services, change networking or disable the firewall.

1.2 — Web-content tampering and evidence

Shared concept →. Run commands in elevated PowerShell inside the Windows VM. The instructor confirms the Default Web Site uses C:\inetpub\wwwroot and starts with the operational page. This round simulates an attacker who already has administrative access.

Prepare a trusted recovery copy

Instructor: use a new exercise directory; the guard prevents overwriting an earlier round’s evidence. Retain this directory through the debrief.

$site = 'C:\inetpub\wwwroot\index.html'
$case = 'C:\CCDC-Exercise-1-2'
if (Test-Path $case) { throw 'Existing exercise directory: ask the instructor to archive it first.' }
if (-not (Test-Path $site)) { throw 'Confirm the IIS physical path before proceeding.' }
New-Item -ItemType Directory -Path $case | Out-Null
Copy-Item -LiteralPath $site -Destination "$case\original.html"
Get-FileHash -LiteralPath $site | Format-List
(Invoke-WebRequest http://172.29.242.40/index.html -UseBasicParsing -TimeoutSec 5).Content

Red team — change the page

Set-Content -LiteralPath 'C:\inetpub\wwwroot\index.html' -Value 'CCDC exercise: changed page' -Encoding UTF8

Blue team — investigate before restoring

Use your campus laptop to open the Windows website with a fresh request. The request may succeed while the expected content is missing. In the VM:

$site = 'C:\inetpub\wwwroot\index.html'
$case = 'C:\CCDC-Exercise-1-2'
Get-Service W3SVC
Get-Item -LiteralPath $site | Select-Object FullName,Length,LastWriteTimeUtc
Get-FileHash -LiteralPath $site
Get-FileHash -LiteralPath "$case\original.html"
Copy-Item -LiteralPath $site -Destination "$case\changed.html"
Get-Content -LiteralPath $site
Get-Acl -LiteralPath $site | Format-List

Review recent IIS access records at the configured logging location (normally C:\inetpub\logs\LogFiles\W3SVC1). They show requests, not who edited the file. File-change attribution requires auditing enabled before the change; do not infer an attacker identity from a timestamp alone.

Blue team — recover and verify

Copy-Item -LiteralPath 'C:\CCDC-Exercise-1-2\original.html' -Destination 'C:\inetpub\wwwroot\index.html' -Force
Get-FileHash -LiteralPath 'C:\inetpub\wwwroot\index.html'
(Invoke-WebRequest http://172.29.242.40/index.html -UseBasicParsing -TimeoutSec 5).Content

Success: the restored hash matches the original, the laptop sees “CCDC Windows intranet: operational”, and DNS still answers. Explain why HTTP 200 alone was insufficient. Instructor archives the evidence directory before the next round.

1.3 — Firewall tampering versus service failure

Shared concept →. Run guest commands in elevated PowerShell. Before the round, confirm Windows Firewall is enabled, IIS is running, and a campus laptop can retrieve the Windows page. Keep the instructor’s VM console available.

Red team — introduce one HTTP-only rule

$rule = 'CCDC-Exercise-HTTP-Block'
if (Get-NetFirewallRule -Name $rule -ErrorAction SilentlyContinue) { throw 'Exercise rule already exists.' }
New-NetFirewallRule -Name $rule -DisplayName $rule -Direction Inbound -Action Block -Protocol TCP -LocalPort 80 -Profile Any

Blue team — investigate

Repeat the laptop HTTP request; expect failure while RDP and DNS remain available. A TCP connection to the relay does not prove the guest HTTP service works.

Get-Service W3SVC,DNS
Get-NetTCPConnection -State Listen | Where-Object LocalPort -eq 80
Get-NetFirewallProfile | Select-Object Name,Enabled
Get-NetFirewallRule -Enabled True -Direction Inbound -Action Block |
  Select-Object Name,DisplayName,Action,Profile
Get-NetFirewallRule -Name 'CCDC-Exercise-HTTP-Block' | Format-List
Get-NetFirewallRule -Name 'CCDC-Exercise-HTTP-Block' | Get-NetFirewallPortFilter
Resolve-DnsName www.training.test -Server 172.29.242.40 -DnsOnly -NoHostsFile

Preserve the rule properties and the before/after observations. Explain why a running service can still be unreachable. A local HTTP check is useful but does not replace the external test.

Blue team — recover

Remove-NetFirewallRule -Name 'CCDC-Exercise-HTTP-Block'
Get-Service W3SVC,DNS
(Invoke-WebRequest http://172.29.242.40/index.html -UseBasicParsing -TimeoutSec 5).Content

Success: the exact exercise rule is absent, the laptop retrieves the operational page, DNS works, and legitimate RDP access remains. Remove only this rule; leave the firewall enabled. The instructor can run the same removal command from the guest console if recovery is needed.

1.4 — Compromised account and excessive privilege

Shared concept →. Use a dedicated exercise account, never a student or instructor account. This round simulates credentials for an account that was improperly granted administrator membership.

Instructor — prepare the dedicated account

Inside elevated Windows PowerShell, set a temporary lab-only password at the prompt and give it to the red team. Confirm the account name is unused. This exercise uses local runas and does not require granting RDP access.

$name = 'ccdc-red-demo'
if (Get-LocalUser -Name $name -ErrorAction SilentlyContinue) { throw 'Account exists: choose a fresh exercise account.' }
$password = Read-Host 'Temporary exercise password' -AsSecureString
New-LocalUser -Name $name -Password $password -Description 'Dedicated CCDC account exercise'
$admins = Get-LocalGroup -SID 'S-1-5-32-544'
Add-LocalGroupMember -Group $admins.Name -Member $name
Get-LocalGroupMember -Group $admins.Name

Red team — demonstrate access

Run this in a separate PowerShell window and enter the temporary password. The new window stays open so the instructor can observe the session.

runas /user:.\ccdc-red-demo "cmd.exe /k whoami /all"

Observe the identity and token groups. UAC may filter administrator privileges in this window; group membership does not mean every process is elevated. No service stop is needed for this account exercise.

Blue team — investigate and contain

Get-LocalUser -Name 'ccdc-red-demo' | Format-List Name,Enabled,LastLogon,Description
$admins = Get-LocalGroup -SID 'S-1-5-32-544'
Get-LocalGroupMember -Group $admins.Name
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4624,4720,4732; StartTime=(Get-Date).AddMinutes(-30)} -ErrorAction SilentlyContinue |
  Select-Object TimeCreated,Id,Message | Format-List

Preserve the account details, unexpected membership and available events. Account creation/group changes require the corresponding audit policy; missing events do not prove no change occurred. The instructor records and checks auditing before class.

Disable-LocalUser -Name 'ccdc-red-demo'
$admins = Get-LocalGroup -SID 'S-1-5-32-544'
Remove-LocalGroupMember -Group $admins.Name -Member 'ccdc-red-demo'
Get-LocalUser -Name 'ccdc-red-demo' | Select-Object Name,Enabled
Get-LocalGroupMember -Group $admins.Name

Disabling an account and removing group membership do not revoke existing process tokens. Have the instructor close the dedicated runas window and confirm its processes have ended in Task Manager’s Details view with the User name column enabled. In a real incident, investigate and terminate all affected sessions/processes or use a planned restart.

Verify and clean up

Repeat the runas command with the same correct password: expect denial. Confirm legitimate student access, the IIS operational page and DNS still work. After the debrief and evidence retention, the instructor removes only the dedicated account:

Remove-LocalUser -Name 'ccdc-red-demo'

Success: identify the excessive privilege, disable new access, end the existing exercise process, and demonstrate legitimate services still work. Prepare a fresh account before reversing roles.

Module 2 — Attacker starts without system access

Read Module 2 concepts and exercise boundaries in Getting Started, then complete the platform tasks below. This track includes a bounded port pass, request-log investigation and a supplied DoS evidence exercise.

2.1 — Port scanning and service discovery

Use the assigned guest only. In these single-VM simulations, the red-team operator uses a normal guest terminal to generate network requests; target administration is reserved for the blue team. The operator login is a traffic-generation convenience, not evidence of a successful intrusion. Do not elevate the red-team commands.

Blue team — establish the service inventory

Record listening ports before the red-team pass. The instructor confirms TCP 65000 is unused; if it is in use, omit it. Required ports are 53 (DNS), 80 (HTTP), and 3389 (RDP).

Get-Date -Format o
Get-NetTCPConnection -State Listen | Sort-Object LocalPort | Select-Object LocalAddress,LocalPort,OwningProcess
Get-Service DNS,W3SVC,TermService

Red team — one bounded pass

Probe only these four ports once. A failed connection can mean a closed port or filtering; it is not a conclusive firewall diagnosis. Save the displayed results for comparison.

53,80,3389,65000 | ForEach-Object {
  $port = $_
  $open = Test-NetConnection -ComputerName 172.29.242.40 -Port $port -InformationLevel Quiet -WarningAction SilentlyContinue
  [pscustomobject]@{Port=$port; TcpReachable=$open}
}

Blue team — explain and verify

  1. Compare probe results with the inventory. Explain each expected listener and investigate any discrepancy.
  2. Inspect existing firewall or service logs for the recorded time window. A connection-only probe may leave no application log entry. Report that visibility gap rather than inventing evidence.
  3. Explain one restriction you would consider for an unnecessary service. This round changes no firewall or service configuration.
  4. Use a fresh laptop request to the assigned website to confirm ordinary HTTP still works.

Complete: show the four results, the matching listener inventory, and a normal HTTP response. No configuration cleanup is needed. The local pass does not establish laptop reachability or test the relay firewall. Windows TCP 53 does not verify UDP DNS.

2.2 practical — Investigate failed Windows authentication

Defender, elevated PowerShell: establish the baseline. The instructor verifies that failure auditing is enabled and that the test name does not exist. The account lookup must return False.

Get-Date -Format o
Get-Service W3SVC,DNS,TermService
[bool](Get-LocalUser | Where-Object Name -eq 'ccdc-probe-no-user')
auditpol /get /subcategory:"Logon"

Understand these commands: Get-Service · Get-Date · Where-Object · script syntax

Operator, a separate PowerShell window: run once and enter arbitrary dummy text at the password prompt. Expect a logon failure; no command window should open. Repeat manually at most twice more if instructed.

runas /user:.\ccdc-probe-no-user "cmd.exe /c whoami"

Understand these commands: whoami

This tests a local logon path, not remote RDP. Expect local/blank source information and inspect the actual logon type. The instructor can additionally demonstrate one rejected RDP login through the lab's existing connection route, using the same nonexistent account. NLA and authentication method can change the logon type and event sequence; do not assume every failed RDP attempt is type 10. The relay may hide the original client IP.

Defender, elevated PowerShell: inspect recent failures and successes. Read the full message for an event containing the test username; unrelated background events may appear too.

$since = (Get-Date).AddMinutes(-10)
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625; StartTime=$since} |
  Select-Object -First 20 TimeCreated,Id,Message | Format-List
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4624; StartTime=$since} |
  Select-Object -First 10 TimeCreated,Id,Message | Format-List

Understand these commands: id · Get-Date · Get-WinEvent · Select-Object · script syntax

Find the target account, time, logon type, status/substatus and source where populated. Event 4625 records failed logon; 4624 records successful logon. Do not confuse the Subject account with the account being targeted. No matching events: verify the time window, audit policy and permissions; do not repeatedly generate failures. One attempt can cause multiple records. Compare an isolated mistake with a cluster of failures; discuss spraying across accounts without performing it.

2.3 practical — Investigate IIS probing and a dummy exposed backup

The instructor first publishes the dummy exercise file. Operator, PowerShell: run these requests once each. Use curl.exe explicitly; curl can be a PowerShell alias on this server.

curl.exe -i --max-time 5 http://172.29.242.40/index.html
curl.exe -i --max-time 5 http://172.29.242.40/ccdc-probe-missing.txt
curl.exe -i --max-time 5 http://172.29.242.40/ccdc-probe-backup.txt

Understand these commands: curl

Expect 200 for the operational page, 404 for the missing path and 200 with dummy text for the published backup. No valid server login was needed to read that file.

Defender, elevated PowerShell: find the website ID and log location in IIS Manager: Sites → Default Web Site → Logging. These commands assume the default W3C path and site ID 1; substitute the actual location if different.

$logRoot = "$env:SystemDrive\inetpub\logs\LogFiles\W3SVC1"
$log = Get-ChildItem -LiteralPath $logRoot -Filter '*.log' |
  Sort-Object LastWriteTime -Descending | Select-Object -First 1
if ($null -eq $log) { throw 'No IIS log found; ask the instructor to check logging.' }
Get-Content -LiteralPath $log.FullName -TotalCount 5
Get-Content -LiteralPath $log.FullName -Tail 60

Understand these commands: Select-Object · Sort-Object · script syntax

W3C log records can be buffered: wait up to a minute and reread; ask the instructor if evidence is still missing. Read the #Fields: header rather than assuming column positions. Identify date, time, c-ip, cs-method, cs-uri-stem, sc-status and, if present, substatus. W3C timestamps are UTC; compare with the timezone shown by Get-Date. A suspicious path is a clue; a 200 with dummy contents demonstrates exposure, not execution or compromise.

Mitigate, repeat and verify

Preserve the relevant records. The following assumes the default website root; the instructor must confirm the physical path first. Verify the file contains only the exercise marker, then remove this file only.

Get-Content -LiteralPath 'C:\inetpub\wwwroot\ccdc-probe-backup.txt'
Remove-Item -LiteralPath 'C:\inetpub\wwwroot\ccdc-probe-backup.txt' -Confirm
curl.exe -i --max-time 5 http://172.29.242.40/ccdc-probe-backup.txt
(Invoke-WebRequest http://172.29.242.40/index.html -UseBasicParsing -TimeoutSec 5).Content
Resolve-DnsName www.training.test -Server 172.29.242.40 -DnsOnly -NoHostsFile
Get-Service W3SVC,DNS,TermService
Get-Content -LiteralPath $log.FullName -Tail 20

Understand these commands: curl · Get-Service · Resolve-DnsName · Invoke-WebRequest · test · script syntax

Expect 404 for the removed backup, the operational Windows intranet, DNS answer 172.29.242.30, and Running services. Allow for IIS log buffering. Discuss unique passwords, supported MFA, restricted administrative reachability and temporary throttling. Aggressive account lockouts can also deny legitimate users access. Do not change shared account policies, RDP rules or host firewall settings during this lesson.

Practice check: show a rejected logon and its evidence; explain why a local source differs from network evidence; show the web exposure before and after mitigation. Give one benign explanation and one suspicious pattern, state the limits of the evidence, and show legitimate services still work. No written report is required.

References: Microsoft failed-logon event 4625; IIS logging and W3C fields; Audit policy inspection.

2.4 — Investigate suspicious request traffic

Use the assigned guest only. In these single-VM simulations, the red-team operator uses a normal guest terminal to generate network requests; target administration is reserved for the blue team. The operator login is a traffic-generation convenience, not evidence of a successful intrusion. Do not elevate the red-team commands.

Prepare

The instructor confirms access logging is enabled and the two probe paths below do not exist. The blue team records the time and normal page response. This exercise uses web access logs as network-request evidence; it is not a packet-capture exercise.

Red team — generate a short request sequence

Run once: four sequential requests, separated by one second. The unique marker distinguishes the round from background traffic. Give the marker to the blue team after it locates the pattern.

$marker = 'ccdc24-' + (Get-Date -Format yyyyMMddHHmmss)
"Round marker: $marker"
'index.html','ccdc24-missing.txt','ccdc24-backup.zip','index.html' | ForEach-Object {
  curl.exe --max-time 5 -sS -o NUL -w "%{http_code} %{url_effective}\n" "http://172.29.242.40/$_`?round=$marker"
  Start-Sleep -Seconds 1
}

Blue team — find and interpret the evidence

$logRoot = 'C:\inetpub\logs\LogFiles\W3SVC1'
$log = Get-ChildItem -LiteralPath $logRoot -Filter '*.log' | Sort-Object LastWriteTime -Descending | Select-Object -First 1
if ($null -eq $log) { throw 'Ask the instructor to verify the IIS log location and logging.' }
Get-Content -LiteralPath $log.FullName -TotalCount 8
Get-Content -LiteralPath $log.FullName -Tail 150 | Select-String 'ccdc24-'

Use the actual configured log path if it differs. IIS records may be buffered: wait up to one minute and reread once. Read its #Fields header; the instructor should enable date, time, c-ip, cs-method, cs-uri-stem, cs-uri-query and sc-status. Nginx combined logs include the request path and query. Distinguish local time offsets from IIS UTC.

  1. Locate the four requests and record time, source, method, path and status.
  2. Explain why the two index requests are ordinary checks and why the backup-like path warrants investigation. Expected status order: 200, 404, 404, 200. If different, investigate the actual site configuration.
  3. Explain why a missing-file request does not demonstrate compromise. A source address identifies a connection, not a person.
  4. Propose one response if a sensitive backup really were exposed: preserve evidence and remove the exposed copy while leaving normal content available.

Verify and close the round

Repeat one normal index request and confirm operational content. Retain the relevant log lines; do not clear the logs. No files, accounts or rules were changed. Reverse roles with a new marker. Complete: show the ordered requests, explain their significance and uncertainty, and demonstrate normal service.

2.5 — Investigate denial of service and resource exhaustion

This is a concrete offline investigation using a supplied synthetic incident dataset. It does not generate a flood or change the live service. The red team introduces the incident evidence; the blue team diagnoses it, proposes containment, and validates the recovery evidence.

Open the evidence inside your assigned VM

Save the Windows incident CSV into Downloads inside the VM. If viewing this pack on a laptop, copy the CSV into the VM first. The commands below use that Downloads path; adjust it if needed. Each row is a one-minute measurement. requests and http_5xx are counts; p95_ms is the 95th-percentile response time in milliseconds; cpu_pct and memory_pct are percentages. The documentation-range source IP is fictional and must not be contacted.

Red team — present the scenario

Tell the blue team: “Users report slow pages and intermittent errors starting at 10:02 UTC. The service monitor still reports the web service running.” Provide the CSV. Do not stop the real service or send load traffic.
